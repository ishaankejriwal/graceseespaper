# External audit prompt

Copy everything below the line to whoever (or whatever) is auditing. It assumes they have a
clone of the repository, checked out at the commit that added this file, which they can find
for themselves with `git log -1 --format=%H -- docs/EXTERNAL_AUDIT_PROMPT.md` on branch `main`.
They also need a working Python environment (`pip install -r requirements-lock.txt`), plus the
raw inputs listed in README section 4 if they want to rerun anything. Nothing in the audit
requires a GPU.

---

You are auditing a research repository for a paper that proposes a per-basin Kalman
filter as the reference forecast for deseasonalized GRACE terrestrial water storage
anomalies, and compares it (and one linear extension of it) with a published deep-learning
forecast product on two mascon solutions. Audit commit: the commit that added this file,
`git log -1 --format=%H -- docs/EXTERNAL_AUDIT_PROMPT.md`, on branch `main`.
Treat every claim below as unverified until you have checked it yourself against the
files named. Report what is wrong, ranked by how much it would change a conclusion.
Do not report things you did not check.

Start by reading, in this order: `README.md`, `docs/STUDY_CONTEXT.md`,
`docs/CODE_MAP.md`, `results/README.md`, and the last three entries of
`results/RUN_LOG.md`. Then run `.venv/Scripts/python.exe scripts/run_chain.py --list` and
`.venv/Scripts/python.exe -m pytest tests -q` (use the project venv's python throughout, not
whatever `python` resolves to on your PATH).

Audit the following. Pick any subset; state which ones you did.

1. The reference forecast. `src/gracefc/kalman.py`. Is the model exactly what the
   documentation says (AR(1) state, additive observation noise, three parameters per
   basin and fold, fit on training months only by L-BFGS-B from four starts, forecast
   at lead h is rho^h times the filtered state at the issue month)? Can any training
   statistic or parameter see a test month? How are missing months and the 2017-18
   mission gap handled in the filter, and is that handling the same in training and
   in forecasting?

2. Deseasonalization and standardization. `src/gracefc/decompose.py` and the fold
   logic in `src/gracefc/evaluate.py` (`DEFAULT_FOLDS`, `split_fold`, and the leakage
   checks in `assert_no_leakage` at L68-77), not `experiment.py`. The trend and harmonics are supposed to be
   estimated on the training window only, per basin and per fold, and the per-basin
   standard deviation likewise. Confirm by reading the code and by checking one basin
   numerically. Would a different but equally reasonable recipe change the ranking of
   models?

3. The comparison with the published product. `scripts/build_li_basin_series.py`,
   `src/gracefc/comparison.py`, `scripts/run_phase6_li_comparison.py`. The product is
   a 1-degree global grid; the study works on basins. Check how the grid is averaged
   onto basins, how non-finite cells are excluded, how the product's own seasonal and
   trend terms are handled to put it into the study's target space, and whether the
   `joint_full_cells` subset rule (a basin must fully contain at least one native
   mascon and at least one valid 1-degree product cell) is applied identically for the
   CSR and JPL products. Look for anything that could favour either side: row
   matching, standardization by one side's variance, months where one side is missing.

4. The strongest own-basin model at leads 1 to 4. `src/gracefc/experiment_flat12.py`,
   `scripts/run_flat12_ridge.py`. The 12-month history windows of filtered state and
   ERA5 must end at the issue month for every lead. Find any path by which a feature
   could include a month after the issue date. Check the ERA5 alignment and the
   handling of windows that overlap missing months.

5. Statistics. `src/gracefc/stats.py`. The Diebold-Mariano test and the moving-block
   bootstrap must be computed on identical row sets for the two models compared; the
   code is supposed to raise if they differ. Verify that this assertion exists and is
   reached by the ladder and comparison scripts. Check the block-length rule and the
   pooling across basins and months for the DM statistic.

6. Reproducibility. Pick one headline number from `results/paper_baseline_contrasts.csv`
   and one from `results/phase6_li_comparison_headline.csv` and recompute each from the
   row-level predictions. The ladder and its contrasts are built from
   `results/phase2_baseline_predictions.csv`, `results/kalman_predictions.csv` and
   `results/flat12_ridge_predictions.csv`; the Li headline from
   `results/phase6_li_comparison_predictions.csv`. None of those four files is stored in
   git, because of their size. They are regenerated by the default chain, so run it (or
   the steps that write them) before attempting this item. Report the difference.

7. The JPL replication. `results/jpl/RUN_PROVENANCE.md` and the headline CSVs under
   `results/jpl/`. Are the folds, deseasonalization, subset rule and statistics the
   same as CSR? Row-level JPL predictions are not in the repository; state clearly
   what you could and could not verify without them.

8. Documentation honesty. Does anything in `README.md` or `docs/` claim a result that
   is not in a results file, or describe a step the chain no longer runs? Are the
   runtimes stated plausible given `results/RUN_LOG.md`?

9. The dropped claims. The neighbor-basin experiments, the mission-split noise model
   and the sequence models are retained as extended chain steps but no longer
   claimed. Is the reason given for dropping each one supported by the results files
   cited? For the neighbor experiments the reason is the JPL non-replication, tabulated
   per lead and per arm in the `results/RUN_LOG.md` entry "JPL neighbor experiments:
   non-replication record (from results/jpl/, collaborator run 2026-09-05/06)". Check
   that entry against `results/jpl/phase3b_summary.csv` and
   `results/jpl/phase4_surrogate_summary.csv`, and check that the placebo counts quoted
   in `README.md`, `docs/STUDY_CONTEXT.md` and `paper/notes/DECISIONS.md` match it.

Report format: a table with columns (finding, file:line, severity: changes a
conclusion / should fix / cosmetic, how you verified it, suggested fix), then a list of
what you checked and found correct, then anything you could not check and why.
